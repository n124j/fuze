# Fuse Core (Plan 1 of 3) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A single-process TypeScript service that talks to the owner over Telegram (and a local CLI), remembers them through markdown files, runs work through a crash-safe job queue, respects quiet hours and a $1/day budget, and sends nothing outward without the safeguards in place for later plans.

**Architecture:** One Node process. A gateway normalizes channel messages (CLI, Telegram) and routes only the paired owner to the agent loop (LLM + tools). Memory is markdown files. SQLite holds jobs/checkpoints, idempotency records, notifications, budget usage, sessions and owner identity. A scheduler enqueues jobs; a worker runs them. A notifier applies priority, quiet hours and dedup.

**Tech Stack:** Node.js 22 LTS, TypeScript (strict, ESM), vitest, better-sqlite3, zod, grammY (Telegram), @anthropic-ai/sdk, croner (cron with timezone).

**Spec:** `docs/superpowers/specs/2026-11-20-fuse-design.md`

**Later plans (not in this plan):** Plan 2 = Google connectors (Gmail draft-only + gated send, Calendar, Tasks, Drive), approval gate, rules + cheap-model triage, morning briefing content. Plan 3 = Apple Calendar/Reminders, Slack (read-only), launchd packaging, memory consolidation job.

## Global Constraints

- Single Node.js process; TypeScript strict mode; ESM.
- Runs on Windows 11 (development) and macOS (production); no macOS-only code in this plan.
- Timezone is a fixed configured IANA zone, default `America/New_York`; never the OS clock zone.
- Quiet hours default `23:00`–`07:00` (configurable); briefing default `07:30`.
- Daily LLM budget hard cap default `$1.00` USD. Fail closed: unknown model pricing throws.
- Models: cheap `claude-haiku-5-5`, strong `claude-sonnet-5-5` (configurable).
- Owner identified by Telegram user ID set via one-time pairing code; messages from anyone else are silently ignored (no reply, no LLM call).
- Secrets only from environment / `.env` (git-ignored); never logged. Logs must not contain message bodies.
- Any tool flagged `needsApproval` must not execute without `approved: true` in its context (the hook exists now; the first such tool arrives in Plan 2).
- Side-effecting actions go through `runOnce` (idempotency); an action recorded as started but not finished must raise `AmbiguousActionError`, never silently repeat.
- Memory files: `profile.md`, `memory.md`, `daily/YYYY-MM-DD.md` under `<dataDir>/memory/`.
- Pending approvals (Plan 2) expire after 24 hours.

## Review Focus

1. A Telegram message from a non-owner user (or in a group chat) → no reply, no LLM call, no budget spend. (Task 7, Task 10 smoke test)
2. Budget hits the cap mid-job → job pauses and retries after local midnight instead of failing or looping; notifier and briefing paths that need no LLM still work. (Tasks 4, 6)
3. Quiet-hours window that crosses midnight, and DST transition days in `America/New_York` (spring-forward 02:00 gap, fall-back repeated hour). (Task 1)
4. Worker killed after a side effect ran but before the job was marked done → the restart does not repeat the side effect. (Tasks 2, 6)
5. Telegram sends a photo/sticker/empty message or a >4096-char reply is produced, or the Anthropic API returns 429/500 → polite non-crashing behavior; replies are chunked at 4096 characters; API errors are retried with backoff and never double-counted in the budget. (Tasks 5, 7, 9)

### Task 6: Job queue and worker

**Files:**
- Create: `src/queue/queue.ts`, `src/queue/worker.ts`
- Test: `tests/queue.test.ts`, `tests/worker.test.ts`

**Interfaces:**
- Consumes: `Db` (Task 2), `BudgetExhaustedError` (Task 4), `nextLocalTime` (Task 1)
- Produces:
  - `interface Job { id: string; type: string; payload: unknown; checkpoint: unknown | null; status: "queued" | "running" | "done" | "failed"; attempts: number; maxAttempts: number; runAfter: number; lockedAt: number | null }`
  - `class JobQueue { constructor(db: Db, clock?: () => number); enqueue(type: string, payload: unknown, opts?: { runAfter?: number; maxAttempts?: number; dedupeKey?: string }): string; claim(): Job | null; saveCheckpoint(id: string, cp: unknown): void; complete(id: string): void; fail(id: string, error: string): void; defer(id: string, runAfter: number): void; recoverStale(timeoutMs: number): number }`
    - `enqueue` with an existing non-failed `dedupeKey` returns the existing job id. `fail` requeues with exponential backoff until `maxAttempts`, then marks `failed`. `claim` returns the oldest job with `runAfter <= now`, status `queued`, and marks it `running`.
  - `type Handler = (job: Job, ctx: { checkpoint(cp: unknown): void }) => Promise<void>`
  - `class Worker { constructor(queue: JobQueue, handlers: Record<string, Handler>, opts: { pollMs: number; staleMs: number; onBudgetPause: () => number /* returns runAfter ms */ }); tick(): Promise<boolean>; start(): void; stop(): Promise<void> }`
    - `tick` runs recoverStale, claims one job, runs its handler, and completes it. A handler throwing `BudgetExhaustedError` calls `queue.defer(job.id, onBudgetPause())` without incrementing attempts. Any other throw calls `queue.fail`. A job type with no handler is failed immediately.

- [ ] **Step 1: Failing tests**: FIFO claim and `runAfter` respected; `dedupeKey` returns the same id; failure retries then ends `failed` after `maxAttempts`; `saveCheckpoint` persists and a job re-claimed after `recoverStale` sees its checkpoint; a job left `running` past `staleMs` is requeued; `BudgetExhaustedError` defers without bumping `attempts`; **crash simulation:** handler performs a `runOnce` side effect, then the process "dies" (job left running); after `recoverStale` the re-run handler calls `runOnce` with the same key and the side effect count stays 1.
- [ ] **Step 2: Run → FAIL**
- [ ] **Step 3: Implement.** Single worker, one job at a time.
- [ ] **Step 4: Run → PASS**
- [ ] **Step 5: Commit** `feat: sqlite job queue with checkpoints and worker`
